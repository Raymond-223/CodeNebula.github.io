    安全基础

    安全不是功能，而是贯穿整个软件开发生命周期的思维模式。本文从密码学基础出发，系统覆盖认证授权、Web 安全、API 安全、基础设施安全、SSDLC 及合规隐私等核心领域，帮助开发者构建纵深防御体系。

    一、密码学基础

    1.1 对称加密

    对称加密使用同一个密钥进行加密和解密。最广泛使用的标准是 AES（Advanced Encryption Standard），支持 128、192 和 256 位密钥。

    from cryptography.hazmat.primitives.ciphers import Cipher, algorithms, modes
from cryptography.hazmat.primitives import padding
import os

def aes_encrypt(plaintext: bytes, key: bytes) -> tuple[bytes, bytes, bytes]:
    iv = os.urandom(16)  # 初始化向量（IV），必须随机
    cipher = Cipher(algorithms.AES(key), modes.GCM(iv))
    encryptor = cipher.encryptor()
    ciphertext = encryptor.update(plaintext) + encryptor.finalize()
    return ciphertext, iv, encryptor.tag  # GCM 模式自带认证标签

    AES 工作模式对比：

    模式 是否需要 IV 并行解密 认证 推荐场景
    ECB ❌ ✅ ❌ 永不使用 — 相同明文块产生相同密文
    CBC ✅ ❌ ❌ 遗留兼容，需配合 HMAC
    GCM ✅ (nonce) ✅ ✅ (AEAD) 强烈推荐 — 同时提供机密性+完整性
    CTR ✅ (nonce) ✅ ❌ 流加密场景，需额外认证

    关键选择： 始终选择 GCM 模式。它提供认证加密（AEAD），在同一操作中同时保证机密性和完整性，避免 CBC + HMAC 组合中容易出现的误用。

    密钥长度建议： AES-128 安全强度足够（128 位密钥对抗暴力破解已远超可行范围），但行业标准已向 AES-256 迁移以应对未来量子计算威胁和合规要求。

    1.2 非对称加密

    非对称加密使用 密钥对（Key Pair）：公钥加密、私钥解密。

    from cryptography.hazmat.primitives.asymmetric import rsa, padding as asym_padding
from cryptography.hazmat.primitives import hashes

# 生成 RSA 密钥对
private_key = rsa.generate_private_key(public_exponent=65537, key_size=2048)
public_key = private_key.public_key()

# 使用公钥加密对称密钥（混合加密常见模式）
ciphertext = public_key.encrypt(
    session_key,
    asym_padding.OAEP(mgf=asym_padding.MGF1(algorithm=hashes.SHA256()),
                      algorithm=hashes.SHA256(), label=None)
)

    非对称算法对比：

    算法 密钥长度 性能 安全性 推荐用途
    RSA 2048/4096 bit 慢 成熟 数字签名、密钥封装
    ECC 256 bit (≈ RSA 3072) 快 相同强度下密钥更短 签名（ECDSA）、密钥交换（ECDH）
    Ed25519 32 byte 极快 高（侧信道抗性强） 推荐：当前最佳签名算法

    数字签名流程：

    // Go — Ed25519 签名与验证
import "crypto/ed25519"

func signMessage(privateKey ed25519.PrivateKey, msg []byte) []byte {
    return ed25519.Sign(privateKey, msg)  // 返回 64 字节签名
}

func verifySignature(publicKey ed25519.PublicKey, msg, sig []byte) bool {
    return ed25519.Verify(publicKey, msg, sig)
}

    1.3 哈希函数

    哈希函数将任意长度输入映射为固定长度的"指纹"。好的哈希函数必须满足：抗原像性（单向）、抗第二原像性（给定输入难找相同哈希的另一输入）、抗碰撞性（难找任意两个相同哈希的输入）。

    import hashlib

# SHA-256 基础用法
digest = hashlib.sha256(b"hello").hexdigest()
# 输出: 2cf24dba5fb0a30e26e83b2ac5b9e29e1b161e5c1fa7425e73043362938b9824

    常见哈希算法安全状态：

    算法 输出长度 碰撞安全 状态
    MD5 128 bit ❌ 可被快速碰撞 禁止使用
    SHA-1 160 bit ❌ SHAttered 攻击 禁止使用
    SHA-256 256 bit ✅ 推荐
    SHA-3-256 256 bit ✅ 推荐（新一代标准）
    BLAKE2b 可变 ✅ 性能优于 SHA-3

    ⚠️ 通行证哈希 ≠ 通用哈希： 不要用 SHA-256 直接哈希密码！必须使用专门的密码哈希函数（见第 2.1 节）。

    彩虹表与盐值： 攻击者可以预先计算海量常见密码的哈希值（彩虹表），快速逆向查找。加盐（Salting）使每个用户即使相同密码也产生不同哈希。

    1.4 密钥交换与 TLS

    Diffie-Hellman 密钥交换 允许双方在不安全的信道上协商共享密钥。ECDH（椭圆曲线 Diffie-Hellman） 是其椭圆曲线版本，更高效。

    sequenceDiagram
    participant Client
    participant Server
    Client->>Server: ClientHello (TLS 版本、密码套件、随机数)
    Server->>Client: ServerHello (选定套件、证书、ServerKeyExchange)
    Client->>Client: 验证证书链（CA 签名）
    Client->>Client: 生成预主密钥，用服务器公钥加密
    Client->>Server: ClientKeyExchange (加密的预主密钥)
    Note over Client,Server: 双方派生会话密钥
    Client->>Server: ChangeCipherSpec + Finished (加密)
    Server->>Client: ChangeCipherSpec + Finished (加密)
    Note over Client,Server: 🔒 HTTPS 安全连接建立

    TLS 1.3 相比 1.2 的关键改进： - 握手从 2-RTT 降至 1-RTT（复用连接 0-RTT） - 移除了不安全的密码套件（RC4、CBC 模式、RSA 密钥交换） - 强制使用 前向保密（Perfect Forward Secrecy） — 即使私钥泄露，过去的会话也无法被解密

    证书链验证路径： 

    根 CA（自签名，预置于操作系统/浏览器）
  └── 中间 CA（由根 CA 签名）
       └── 服务器证书（由中间 CA 签名）
            └── subjectAltName = *.example.com

    二、认证与授权

    2.1 密码存储

    绝对禁止： 明文存储、MD5/SHA-1/SHA-256 直接哈希、Base64 编码、自加密。

    正确做法： 使用专为密码设计的慢速哈希函数。

    import bcrypt

# 注册：生成哈希
password = b"SecureP@ss123!"
salt = bcrypt.gensalt(rounds=12)   # rounds=12 ≈ 250ms
hashed = bcrypt.hashpw(password, salt)

# 登录：验证
if bcrypt.checkpw(input_password, stored_hash):
    print("认证通过")

    密码哈希算法对比：

    算法 设计 抗 GPU/ASIC 可调参数 推荐度
    bcrypt 1999 ⭐⭐⭐ cost factor ★★★★ 广泛使用
    argon2id 2015 (PHC 胜出) ⭐⭐⭐⭐⭐ time/mem/parallel ★★★★★ 首选
    scrypt 2009 ⭐⭐⭐⭐ N/r/p ★★★★ 内存硬
    PBKDF2 2000 ⭐ iterations ★★ CPU 易并行 
    from argon2 import PasswordHasher, Type

ph = PasswordHasher(
    time_cost=3,          # 迭代次数
    memory_cost=65536,    # 64MB 内存消耗
    parallelism=4,        # 并行线程
    hash_len=32,          # 输出哈希长度
    type=Type.ID          # argon2id — 同时抗侧信道和 GPU 攻击
)
hash_str = ph.hash("my_password")
ph.verify(hash_str, "my_password")  # 自动解析参数并验证

    Pepper（密钥胡椒）： 在哈希前追加一个应用级秘密（存储在 HSM 或外部密钥服务中），即使数据库泄露，攻击者也无法离线破解。

    密码策略（NIST SP 800-63B 最新指南）： - 最小长度 8 字符（推荐 12+） - 重点检查常见密码黑名单（top 10000 密码库） - 不再强制要求大小写+数字+符号组合 - 支持所有 ASCII + Unicode 字符 - 允许粘贴密码 - 不强制周期性轮换（除非怀疑泄露）

    2.2 多因素认证（MFA）

    因素类型 示例 安全强度
    知识因素（你知道） 密码、PIN ⭐
    持有因素（你有） TOTP、硬件密钥 ⭐⭐⭐
    固有因素（你是谁） 指纹、面部识别 ⭐⭐

    TOTP（基于时间的一次性密码）实现原理：

    import hmac, struct, time, base64

def generate_totp(secret: str, interval: int = 30) -> str:
    key = base64.b32decode(secret.upper())
    counter = struct.pack(">Q", int(time.time() // interval))
    h = hmac.new(key, counter, "sha1").digest()
    offset = h[-1] & 0x0F
    code = struct.unpack(">I", h[offset:offset+4])[0] & 0x7FFFFFFF
    return f"{code % 1000000:06d}"

    推荐排序： WebAuthn/FIDO2 硬件密钥 > TOTP 应用 > SMS（SMS 易受 SIM Swap 攻击，尽可能避免）。

    2.3 会话管理

    # 安全的会话配置示例（Python Flask）
app.config.update(
    SECRET_KEY=os.environ["FLASK_SECRET"],  # 从环境变量读取，绝不硬编码
    SESSION_COOKIE_HTTPONLY=True,           # 禁止 JavaScript 访问
    SESSION_COOKIE_SECURE=True,             # 仅 HTTPS
    SESSION_COOKIE_SAMESITE='Lax',          # 防 CSRF
    PERMANENT_SESSION_LIFETIME=timedelta(hours=1),
    SESSION_REFRESH_EACH_REQUEST=True       # 滑动过期
)

    会话安全黄金法则： 1. 会话 ID 不可预测 — 使用 os.urandom(32) 或系统 CSPRNG 生成，长度 ≥ 128 位 2. 登录后旋转会话 ID — 防止会话固定攻击（Session Fixation） 3. 登出时销毁会话 — 清除服务器端和客户端会话数据 4. 设置合理超时 — 无操作 15-30 分钟后过期，敏感操作（银行）更短 5. Cookie 属性 — 始终设置 HttpOnly、Secure、SameSite

    2.4 JWT 深入剖析

    JWT（JSON Web Token）由三部分组成：header.payload.signature。

    eyJhbGciOiJSUzI1NiIsInR5cCI6IkpXVCJ9.
eyJzdWIiOiIxMjM0NTY3ODkwIiwibmFtZSI6IkpvaG4gRG9lIiwiaWF0IjoxNTE2MjM5MDIyfQ.
SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c

    关键字段： 

    {
  "alg": "RS256",
  "typ": "JWT",
  "kid": "key-id-1"
}
.
{
  "sub": "user_12345",
  "iat": 1700000000,
  "exp": 1700003600,
  "iss": "https://auth.example.com",
  "aud": "api.example.com",
  "jti": "unique-token-id"
}

    RS256 vs HS256：

    特性 HS256 (HMAC + SHA-256) RS256 (RSA + SHA-256)
    密钥类型 对称（单一密钥） 非对称（公/私钥对）
    签名/验证 同一密钥 私钥签名，公钥验证
    密钥分发 必须安全共享 公钥可公开
    风险 服务端可伪造 Token 仅认证服务器可签发
    推荐 ❌ 不推荐用于微服务 ✅ 标准选择

    ⚠️ 「alg: none」漏洞： 老旧的 JWT 库可能接受 alg: none 的令牌（无签名验证）。务必配置库时指定允许的算法白名单。

    JWT 常见漏洞： 1. 算法混淆攻击 — 服务器预期 RS256，攻击者将 alg 改为 HS256，用泄露的公钥作为 HMAC 密钥签名 2. 过期令牌未正确验证 — 忽略 exp、nbf 声明 3. 敏感数据泄露 — payload 仅 Base64 编码（非加密），JWT 永不应存放密码/信用卡等敏感信息 4. 无绑定到会话 — JWT 无退出机制（除非使用黑名单或短有效期）

    2.5 OAuth 2.0 与 OpenID Connect

    授权码流程（Authorization Code + PKCE）——当前推荐方案：

    ┌─────────┐          ┌───────────┐          ┌──────────┐
│  前端    │          │  后端服务  │          │ 授权服务器│
│ (SPA)   │          │  (API)    │          │ (Auth0)  │
└────┬────┘          └─────┬─────┘          └─────┬────┘
     │                     │                      │
     │  1. 登录请求         │                      │
     │─────────────────────┼─────────────────────>│
     │  2. 授权码（code）    │                      │
     │<────────────────────┼──────────────────────│
     │                     │                      │
     │  3. code + code_verifier 交换令牌            │
     │─────────────────────>                      │
     │                     │   4. 返回 access_token│
     │<────────────────────│──────────────────────│
     │                     │                      │
     │  5. API 请求 + Bearer Token                │
     │─────────────────────>                      │
     │                     │  6. 验证 Token        │
     │                     │<─────────────────────│
     │                     │  7. 返回资源          │
     │<────────────────────│                      │

    为什么需要 PKCE： 传统授权码流程依赖客户端密钥（client_secret），但 SPA/移动端无法安全存储密钥。PKCE 使用动态生成的 code_verifier 和 code_challenge，即使是公开客户端也能安全使用。

    OAuth 2.0 与 OpenID Connect 的关系： - OAuth 2.0：授权框架，关注"能不能访问资源" - OpenID Connect (OIDC)：在 OAuth 2.0 之上添加认证层，关注"你是谁" - OIDC 额外返回 id_token（JWT 格式），包含用户身份信息

    2.6 RBAC vs ABAC vs ReBAC

    模型 全称 核心概念 粒度 适用场景
    RBAC Role-Based Access Control 角色 → 权限 粗 企业管理系统、CMS
    ABAC Attribute-Based Access Control 属性规则（用户/资源/环境） 细 金融、医疗、多云
    ReBAC Relationship-Based Access Control 资源间关系图 动态 Google Drive、GitHub 
    # ABAC 策略示例（使用 Casbin/OPA 风格）
policy = """
允许操作当且仅当：
  user.department == resource.owner_department AND
  user.clearance_level >= resource.required_clearance AND
  time.now() BETWEEN resource.access_window.start AND resource.access_window.end
"""

    三、Web 安全（OWASP Top 10）

    3.1 SQL 注入

    攻击类型： - In-Band（同信道） — 攻击和结果在同一通道返回 - Blind（盲注） — 通过 true/false 响应推断数据 - Out-of-Band（带外） — 通过 DNS/HTTP 请求外传数据

    预防措施：

    # ❌ 错误：字符串拼接
query = f"SELECT * FROM users WHERE username = '{username}' AND password = '{password}'"

# ✅ 正确：参数化查询
import sqlite3
cursor.execute("SELECT * FROM users WHERE username = ? AND password = ?",
               (username, password))

# ORM 方式（SQLAlchemy）
users = session.query(User).filter(User.username == username, User.password == password).all()

    防御层次（纵深防御）： 1. 第一道防线：参数化查询 / ORM — 杜绝拼接 2. 第二道防线：输入验证 — 白名单允许的字符 3. 第三道防线：WAF — 检测已知攻击模式 4. 第四道防线：最小权限原则 — 数据库账户仅具有必要权限

    3.2 XSS（跨站脚本攻击）

    类型 触发方式 持久性 危害
    Stored XSS 存储在数据库，用户访问页面时触发 ✅ 永久 高危 — 所有访问者受影响
    Reflected XSS URL/请求参数中注入，即时反射 ❌ 一次性 需诱导用户点击
    DOM-based XSS 客户端 JavaScript 动态处理不可信输入 ❌ 绕过服务端过滤

    预防策略：

    <!-- CSP（Content Security Policy）HTTP 响应头 -->
Content-Security-Policy: default-src 'self'; 
                       script-src 'self' https://cdn.example.com;
                       style-src 'self' 'unsafe-inline';
                       img-src 'self' data:;
                       object-src 'none';
                       base-uri 'none';

<!-- 输出编码 — 根据上下文使用不同编码策略 -->
<div>${escapeHtml(userInput)}</div>         <!-- HTML 实体编码 -->
<a href="${escapeUrl(userInput)}">...</a>   <!-- URL 编码 -->
<script>var x = ${escapeJs(userInput)}</script> <!-- JavaScript 编码 -->

    不要依赖 X-XSS-Protection — 该标头已被浏览器废弃（Chrome 和 Edge 已移除），CSP 是正确方案。

    3.3 CSRF（跨站请求伪造）

    工作原理： 用户登录 A 站后，在未登出的情况下访问恶意 B 站，B 站构造请求冒用 A 站的用户身份。

    三重防御机制：

    # 1. CSRF Token（服务端验证）

csrf = CSRFProtect(app)  # 为每个表单生成 Token，在服务器验证

# 2. SameSite Cookie（浏览器原生防御）
Set-Cookie: session=abc123; SameSite=Strict; HttpOnly; Secure
# Strict — 完全禁止跨站请求携带 Cookie
# Lax — 允许顶级导航（GET 请求）— 推荐默认值
# None — 允许所有跨站请求（需同时设置 Secure）

# 3. Double Submit Cookie — 将 Token 同时放在 Cookie 和请求头中，
# 服务器验证两者是否一致（适用于无状态架构）

    3.4 SSRF（服务端请求伪造）

    攻击者控制服务端发起请求，访问内部网络资源。

    预防措施：

    import ipaddress
from urllib.parse import urlparse

def validate_url(url: str) -> bool:
    parsed = urlparse(url)
    try:
        # 1. 解析 IP，禁止内网地址
        ip = ipaddress.ip_address(socket.gethostbyname(parsed.hostname))
        if ip.is_private or ip.is_loopback or ip.is_link_local:
            return False
        # 2. 白名单协议
        if parsed.scheme not in ("https",):
            return False
        # 3. DNS rebinding 防护：解析后再次验证
        return True
    except Exception:
        return False

    4.1 速率限制

    # Token Bucket 算法实现
import time
from collections import defaultdict

class TokenBucket:
    def __init__(self, rate: float, capacity: int):
        self.rate = rate          # 令牌填充速率（/秒）
        self.capacity = capacity  # 桶容量（最大突发）
        self.tokens = defaultdict(lambda: capacity)
        self.last_refill = defaultdict(time.time)

    def allow(self, key: str) -> bool:
        now = time.time()
        elapsed = now - self.last_refill[key]
        self.tokens[key] = min(self.capacity,
                               self.tokens[key] + elapsed * self.rate)
        self.last_refill[key] = now
        if self.tokens[key] >= 1:
            self.tokens[key] -= 1
            return True
        return False

# 使用 Redis 的滑动窗口（生产环境推荐）
# 返回 `X-RateLimit-Remaining` / `Retry-After` 头

    九、底层原理：密码学与 TLS 内核

    前面章节介绍了密码学工具"怎么用"，本节深入"为什么这样设计"：AES 轮函数如何实现混淆与扩散，RSA 与 ECC 各自建立在哪个数学难题之上，SHA-256 为何不可逆，TLS 1.3 握手如何协商出会话密钥，以及 HTTPS 证书链如何建立信任。理解内核，才能写出经得起推敲的安全代码。

    9.1 对称加密内核：AES 轮函数与分组模式

    AES-128 将 16 字节明文块排列成 4×4 状态矩阵，迭代 10 轮（AES-192 为 12 轮，AES-256 为 14 轮）。除最后一轮外，每轮执行四个步骤：

    明文块(16B) ──► 轮密钥加(AddRoundKey) ── 与轮密钥异或
                     │
                     ▼
                 字节替换(SubBytes) ── S 盒非线性代换 ──► 混淆(confusion)
                     │
                     ▼
                 行移位(ShiftRows) ── 行循环移位，使列间数据交叉
                     │
                     ▼
                 列混淆(MixColumns) ── GF(2^8) 矩阵乘法 ──► 扩散(diffusion)
                     │
                     ▼
                 轮密钥加(AddRoundKey) ── 进入下一轮
（最后一轮省略列混淆；轮密钥由密钥扩展算法从主密钥派生）
    • 混淆：明文与密钥关系复杂化，单个明文字节变化后，密文每个字节约以 1/2 概率翻转；
    • 扩散：单个明文字节的影响铺满整个状态矩阵，破坏统计结构，抵抗差分与线性分析。

    分组模式对比：

    模式 是否需 IV/nonce 并行解密 认证 典型问题
    ECB 否 是 否 相同明文块产出相同密文块，泄漏模式信息，禁用
    CBC 是（IV） 否 否 需配合 HMAC；IV 必须随机且不可预测
    CTR 是（nonce） 是 否 流式加密，需额外认证
    GCM 是（96-bit nonce） 是 是（AEAD） nonce 重用即灾难，可恢复认证密钥 H

    为什么 CBC 需要 IV： CBC 的迭代式是 C_i = E_K(P_i ⊕ C_{i-1})（C_0 = IV）。若同一密钥下两条消息使用相同 IV，则首个分组 P_1 ⊕ IV 相同、C_1 相同，攻击者可据此探测明文关系。IV 使相同明文在不同会话中产生不同密文——它不必保密，但必须随机且每次唯一。

    为什么 GCM 同时提供认证： GCM 在 CTR 模式下加密的同时，用 GHASH 在 GF(2¹²⁸) 上对密文与附加数据（AAD）做多项式累加，生成 128 位认证标签。GHASH 的密钥 H = E_K(0¹²⁸) 与加密密钥同源，篡改任何一位密文都会导致标签校验失败。机密性（CTR 加密）、完整性（GHASH 标签）由同一密钥与计数器体系完成，即 AEAD——消灭了"先加密后认证"组合中的误用空间。

    核心思想： 分组模式解决"如何用块密码加密任意长度数据"，AEAD 把机密性、完整性、nonce 唯一性合并为单一原语。ECB 泄漏模式、CBC 无认证且 IV 易误用，GCM 是当前唯一推荐选择。

    小结： AES 以"混淆+扩散"轮函数抵抗统计分析；CBC 依赖随机 IV 且无认证，GCM 以 GHASH 一步获得认证加密，成为现代 TLS 的默认选择。

    9.2 非对称加密的数学基础：RSA 与 ECC

    RSA 的数论基础： 取大素数 p、q，令 n = p·q，φ(n) = (p−1)(q−1)。选公钥指数 e（常用 65537）满足 gcd(e, φ(n)) = 1，计算私钥 d ≡ e⁻¹ (mod φ(n))。由欧拉定理 a^φ(n) ≡ 1 (mod n)：

    加密:  c = m^e  mod n
解密:  m = c^d  mod n = m^(e·d) mod n = m^(k·φ(n)+1) mod n ≡ m  (mod n)

    安全性依赖大整数分解难题：已知 n 反求 p、q 目前只有亚指数复杂度的算法（一般数域筛 GNFS）。一旦分解成功，即可由 e 求出 d，私钥沦陷。

    ECC 的椭圆曲线离散对数难题： 选取有限域上的椭圆曲线 E 与基点 G（阶为 n），私钥为随机整数 d，公钥 Q = d·G（标量乘法）。已知 Q 与 G 反求 d 是椭圆曲线离散对数问题（ECDLP），目前仅有指数级算法（Pollard rho），故 256 位曲线即可提供 128 位安全强度。

    RSA 与 ECC 对比：

    维度 RSA ECC（P-256）
    数学难题 大整数分解（GNFS 亚指数） 椭圆曲线离散对数（指数级）
    128 位安全所需密钥 3072 bit 256 bit
    密钥生成 慢（大素数搜索 + 素性检验） 快
    加解密/签名性能 慢 快 5–10 倍
    签名长度 与密钥同长（约 384 B） 64 B
    量子威胁 Shor 算法可破解 Shor 算法同样可破解

    核心思想： 非对称安全的本质是"正反向计算不对称"——正向（加密、验签）容易，反向（解密、伪造）依赖公认困难问题。ECC 因 ECDLP 缺乏亚指数算法，用更短密钥达到同等强度。

    小结： RSA 基于分解难题、ECC 基于 ECDLP；同强度下 ECC 密钥更短、性能更优，但二者均受 Shor 算法威胁，需关注后量子算法（Kyber、Dilithium）迁移。

    9.3 哈希函数原理：SHA-256 与不可逆性

    Merkle–Damgård 结构： SHA-256 将消息填充至 512 位的整数倍（末尾附加 64 位长度字段），再按分组逐块压缩：

    消息 M ─► 填充(补位 + 64bit 长度) ─► M1 ─► M2 ─► … ─► Mk
                                         │      │          │
                                         ▼      ▼          ▼
IV(8×32bit 常量) ─► 压缩函数f ─► 中间态 ─► 压缩函数f ─► … ─► 256bit 摘要
                     (64 轮：模 2^32 加法、循环移位、非线性函数)

    压缩函数 f 接收 512+256 位、输出 256 位，是单向压缩：信息被丢弃，反向求解等价于解 2²⁵⁶ 个方程。

    雪崩效应演示（改动 1 个比特，摘要约半数比特翻转）：

    import hashlib

msg = b"GET /api/user?id=1001 HTTP/1.1"
flipped = bytes([msg[0] ^ 0b00000001]) + msg[1:]  # 翻转首字节最低位

da, db = hashlib.sha256(msg).digest(), hashlib.sha256(flipped).digest()
diff = sum(bin(x ^ y).count("1") for x, y in zip(da, db))

print("原始:   ", hashlib.sha256(msg).hexdigest())
print("翻转1位:", hashlib.sha256(flipped).hexdigest())
print(f"比特翻转率: {diff / (len(da) * 8):.2%}")

    预期输出：
原始:    722c4b7d74a8ea3fb7cc1a560fab19ca150ad50b21c640f4b53b6f51e769b0c6
翻转1位: ebc68ba6f3c7930f866afabcf6a226f67a69fffa3b5aa35950b1041bbe59cd7d
比特翻转率: 53.12%   （理论期望 50%，256 位中约 128 位翻转）

    为什么不可逆： 单向压缩 + 长度压缩（512+256 → 256）构成多对一映射，反函数不存在；可行攻击只有抗原像性穷举（2²⁵⁶）与生日碰撞（2¹²⁸），均远超现实算力。

    彩虹表与加盐： 攻击者预计算"常见密码 → 哈希"的链式表（彩虹表），查表即可逆向弱密码。加盐（每用户随机盐与密码拼接后哈希）使每个用户的哈希空间独立，预计算表整体失效；密码场景还需慢哈希（bcrypt/argon2id）抬高单次猜测成本。

    核心思想： 哈希安全来自"单向压缩 + 雪崩扩散"组合：压缩保证不可逆，雪崩保证输入的任何细微差异在输出中无规律放大，无法通过局部修改构造碰撞。

    小结： Merkle–Damgård 迭代把任意长度输入折叠为定长摘要；不可逆源于信息压缩，防碰撞源于雪崩效应；彩虹表可被加盐彻底瓦解。

    9.4 数字签名：私钥加密摘要、公钥验证

    签名是"只有私钥持有者能产生、任何人都能验证"的完整性凭证：对消息的哈希摘要做私钥运算生成签名，验签用公钥运算并比对：

    ┌───────── 签名方（持有私钥 d）──────────┐      ┌───────── 验证方（持有公钥 Q）──────────┐
│ 消息 M ─► SHA-256 ─► 摘要 h           │      │ 消息 M ─► SHA-256 ─► 摘要 h'          │
│ 摘要 h ─► 私钥运算 sign(h) ─► 签名 s  │ ────► │ 签名 s ─► 公钥运算 verify(s) ─► h''   │
│                                       │ 传输  │ 比对 h' == h'' ? 相等则签名有效       │
└───────────────────────────────────────┘      └───────────────────────────────────────┘

    为什么先哈希再签名（Sign-then-Hash）： - 性能：非对称运算开销与输入长度相关，对定长摘要（32 B）运算远快于对整条消息； - 长度：签名长度与消息长度无关，固定为密钥长度量级； - 安全：哈希破坏消息的代数结构，防止 RSA 乘法同态等性质被利用构造伪造签名。

    from cryptography.hazmat.primitives.asymmetric import rsa, padding
from cryptography.hazmat.primitives import hashes

key = rsa.generate_private_key(public_exponent=65537, key_size=2048)

def sign(msg: bytes) -> bytes:
    return key.sign(msg, padding.PSS(mgf=padding.MGF1(hashes.SHA256()),
                                     salt_length=padding.PSS.MAX_LENGTH),
                    hashes.SHA256())

def verify(msg: bytes, sig: bytes) -> bool:
    try:
        key.public_key().verify(sig, msg,
            padding.PSS(mgf=padding.MGF1(hashes.SHA256()),
                        salt_length=padding.PSS.MAX_LENGTH),
            hashes.SHA256())
        return True
    except Exception:
        return False

sig = sign(b"release-v1.2.3")
print(verify(b"release-v1.2.3", sig))        # True
print(verify(b"release-v1.2.3-tampered", sig))  # False（摘要不匹配）

    核心思想： 签名不是"加密消息"，而是"用私钥对摘要做单向变换"；验证方用公钥还原摘要并与本地哈希比对。哈希层将任意长度消息折叠为定长摘要并抹去代数结构，是签名方案安全性的基石。

    小结： 签名 = 私钥运算（产生）+ 公钥运算（校验）；先哈希同时解决性能、长度与结构安全三个问题，任何字节篡改都会导致摘要不匹配而验签失败。

    9.5 TLS 1.3 握手全流程与前向保密

    TLS 1.3 握手仅需 1-RTT，且默认全部使用临时密钥（ephemeral）实现前向保密：

    Client                                            Server
  │ 1. ClientHello                                  │
  │    key_share: 客户端 ECDHE 临时公钥               │
  │    supported_versions: [1.3]                    │
  ├────────────────────────────────────────────────►│
  │                                                 │ 2. ServerHello
  │                                                 │    key_share: 服务器 ECDHE 临时公钥
  │                                                 │ 3. 证书 + 证书链（含签名）
  │ 4. 校验证书链（CA 信任）                         │
  │    计算共享秘密：ECDHE(双方临时私钥)              │
  │    派生主密钥与流量密钥                           │
  │ 5. Finished（应用数据加密自此开始）               │
  │◄────────────────────────────────────────────────┤
  │ 6. Finished + 应用数据                          │
  ├────────────────────────────────────────────────►│
  │ 7. 应用数据（AES-256-GCM，双向）                 │
  │◄════════════════════════════════════════════════►│

    密钥派生链： ECDHE 共享秘密 → HKDF-Extract → 主密钥 → HKDF-Expand → 会话密钥（客户端/服务器各一套读写密钥：AES-256-GCM + 派生 IV）。

    前向保密原理： 每次握手生成全新的 ECDHE 临时密钥对，会话密钥由临时私钥参与派生，握手结束后临时私钥立即销毁。即使长期密钥（证书私钥，仅用于签名认证）日后泄露，攻击者也拿不到已销毁的临时私钥，无法回溯解密历史流量。TLS ≤1.2 的 RSA 密钥交换用证书私钥直接加密预主密钥，不具备此性质，故在 TLS 1.3 中被彻底移除。

    # ECDHE 密钥协商演示
from cryptography.hazmat.primitives.asymmetric import ec
from cryptography.hazmat.primitives import hashes
from cryptography.hazmat.primitives.kdf.hkdf import HKDF

alice = ec.generate_private_key(ec.SECP256R1())
bob   = ec.generate_private_key(ec.SECP256R1())

# 交换公钥后各自计算共享秘密（两端得到相同字节）
shared_a = alice.exchange(ec.ECDH(), bob.public_key())
shared_b = bob.exchange(ec.ECDH(), alice.public_key())
assert shared_a == shared_b  # 共享秘密一致

# HKDF 派生会话密钥
session_key = HKDF(algorithm=hashes.SHA256(), length=32,
                   salt=None, info=b"tls13 traffic").derive(shared_a)
print(f"共享秘密: {shared_a.hex()[:32]}...")
print(f"会话密钥: {session_key.hex()}")
# 预期输出: 两条 32 字节十六进制串；两端共享秘密完全一致

    核心思想： 认证（证书签名，长期密钥）与机密性（ECDHE，临时密钥）解耦——长期密钥只证明身份，临时密钥只加密数据。这是 TLS 1.3 前向保密的本质，也是"用后即焚"在密钥管理中的体现。

    小结： TLS 1.3 以 ECDHE 临时密钥协商共享秘密、HKDF 派生会话密钥，1-RTT 完成握手；临时私钥即时销毁，保证长期密钥泄露后历史流量依然安全。

    9.6 HTTPS 证书链：CA 信任模型与吊销

    信任链结构： 浏览器内置根 CA 证书（信任锚），服务器证书由中间 CA 签发，中间 CA 由根 CA 签发：

    ┌──────────────┐ 签发  ┌──────────────┐ 签发  ┌──────────────┐
│  根 CA(自签)  │ ────► │  中间 CA      │ ────► │  服务器证书   │
│  内置信任锚    │       │  (Sub CA)     │       │  www.example │
└──────────────┘       └──────────────┘       └──────────────┘
   验证路径：叶子 ← 中间 ← 根（逐级用上级公钥验证下级签名，直至信任锚）

    X.509 v3 证书结构：

    字段 含义
    version / serialNumber 版本（v3）与唯一序列号
    issuer / subject 签发者与持有者 DN
    validity 有效期（notBefore / notAfter）
    subjectPublicKeyInfo 持有者公钥与算法标识
    extensions SAN（域名）、Key Usage、EKU、CRL/OCSP 地址
    signatureAlgorithm + signature 签发者对上列字段的签名

    验证流程：① 用上级证书公钥验证本证书签名；② 检查有效期；③ 检查域名与 SAN 匹配；④ 检查 Key Usage/EKU；⑤ 查询吊销状态。

    吊销机制： - CRL（证书吊销列表）：CA 定期发布被吊销序列号列表，客户端下载比对。缺点：列表体积大、更新滞后，吊销到生效存在窗口期； - OCSP（在线证书状态协议）：客户端实时查询单证书状态（good/revoked/unknown）。缺点：额外网络请求，且 CA 可获知用户访问的站点（隐私泄露）；OCSP Stapling 由服务器在握手中附带经签名的响应，消除该问题。

    核心思想： HTTPS 信任不是"验证证书本身"，而是"验证签名链追溯到信任锚"。根 CA 私钥是全系统信任的单点——一旦泄露（如 DigiNotar 事件）必须立即吊销其签发的所有证书，故根 CA 私钥通常离线存储。

    小结： 证书链把分散的站点信任收敛到少数根 CA；X.509 承载公钥与元数据并由上级签名防篡改；CRL 批量滞后、OCSP 实时但有隐私成本，OCSP Stapling 是折中方案。
